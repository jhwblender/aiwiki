# CLAUDE.md

AI-integrated company wiki. People use it like a normal wiki. A built-in assistant can search and read the wiki to answer questions, and it turns new information (chat messages, and later dropped or watched files) into proposed edits that anyone can approve or reject inline on the page.

Audience: a small group first, then wider use. Most reviewers are not programmers.

## Commands

- `./start.sh` is the one-command start for people running the wiki: checks Node/npm/git (offering to download Node 22 into `~/.local/share/aiwiki/node` when it is missing), installs packages when they are missing or the package list changed (with plain-language fixes when an install fails), creates `.env.local`, rebuilds into `.next-prod` only when code changed, and starts the optimised server (`--dev`, `--open`, `--shortcut` for a Windows desktop launcher). It starts at `PORT` (default 3000) and moves to the next free port when that one is taken, remembering it in `.aiwiki-port`
- `./stop.sh` stops the wiki started by `./start.sh`, following `.aiwiki-port`; `PORT=3001 ./stop.sh` stops one on a chosen port, and it only stops a Next.js server
- `npm run dev` starts the development server on http://localhost:3000
- `npm run build` type checks and builds; run it before calling any change done (while `npm run dev` is running, use `NEXT_DIST_DIR=.next-e2e npx next build` so the two do not share `.next`)
- `npm run e2e` runs the end-to-end check (needs nothing running; uses ports 3100 and 4556)
- `npm run mock-llm` starts the scripted mock model on port 4555; set `LOCAL_LLM_BASE_URL=http://127.0.0.1:4555/v1` to click through the UI without a real model
- Config lives in `.env.local` (see `.env.example`); data lives in `./data` (`WIKI_DATA_DIR`)
- Delete `./data` to reset to the seed wiki

## Architecture

- **Next.js 15 (App Router, TypeScript)**: one app serving the UI and the REST API
- **`lib/wiki.ts`**: pages are markdown files in `data/wiki/`, which is a git repo. All git calls go through `serial()` so concurrent writes never collide. Search is SQLite FTS5, rebuilt from the files on startup
- **`lib/diff.ts`**: paragraph-level diff (blocks split on blank lines). A hunk is one run of removed and added blocks and is the unit a reviewer approves. Each hunk has a fingerprint so stale approvals are rejected. `rebase` replays a suggestion onto a page that changed since it was written; overlapping paragraphs make it a conflict that can only be rejected
- **`lib/proposals.ts`**: sources, change sets, proposals, decisions and page_sources (schema in `lib/db.ts`)
- **`lib/ai/`**: `providers.ts` (registry and Anthropic adapter), `local.ts` (OpenAI-compatible adapter for Ollama, LM Studio and vLLM, plus the Settings connection test; requests go through `node:http`, not `fetch`, because Node's fetch gives up after five minutes without a reply whatever timeout is set, and a large model on a long prompt takes longer), `tools.ts` (wiki tools), `agent.ts` (tool loop, max 10 steps)
- **Pending awareness**: `read_page` shows the approved page plus a separately labelled list of other people's pending suggestions. Each chat sends a `chatId`; a later message in the same chat (same name) edits on top of that chat's pending suggestion and supersedes it (`proposals.superseded_by`), and approval records every message in the chain as a source
- **Page structure**: paths nest up to 5 levels; every page lists its sub-pages and sidebar folders open their section. `movePage` in `lib/wiki.ts` moves a page with everything under it and rewrites `[[links]]` and `/wiki/` links on every page in one commit; `movePageWithRecords` in `lib/proposals.ts` carries pending suggestions, sources and structural suggestions along
- **Structural suggestions**: the assistant's `move_page` and `remove_page` tools stage rows in `page_ops`, shown as a card on the page with Approve and Reject (`/api/ops/:id`, decisions in `op_decisions`). Splits and merges combine these with the normal edit tools
- **Files (`lib/files.ts`)**: uploads go to `/api/files`, are classified by their first bytes (PDF, docx, text, PNG, JPEG, GIF, WebP; 25 MB, 10 per message) and stored once per SHA-256 under `data/assets/`. Extracted text is cached in `file_text` by hash: PDF text layer via unpdf, scanned pages rendered with @napi-rs/canvas and read by the vision model, Word via mammoth, photos described by `provider.describeImage`. The agent reads attachments before its loop and passes them inside `<<<Attached file>>>` markers as information, not instructions. Each file becomes a `file` source (filename, hash, version, stored path); extra files in one message link through `change_set_sources`. Originals open from the source chip (`/api/sources/:id/file`); photos can be shown on pages with `/api/files/:id`
- **Documents and versions (`lib/ingest.ts`)**: every file belongs to a document (`drop:<name>` for drops, later `folder:<label>:<path>`), and each distinct content is a version. `checkVersion` decides new, unchanged or changed without writing; `recordVersion` writes only after the assistant finished, so failures can be retried. An unchanged file is pointed out (and skipped in the queue); a changed one is reduced to the paragraphs that changed
- **Ingest queue (`lib/queue.ts`)**: `ingest_jobs` processed one at a time by an in-process worker, resumed at startup by `instrumentation.ts` (Node-only code lives in `instrumentation-node.ts`). Jobs run the same agent as the chat, with the model picked in the chat. Chat offers "File in the background". Settings shows counts per status (filterable), the running job with a live log of its steps and Stop, Pause and Resume (stored as `queue.paused` in `settings`; the running file finishes first), Cancel per job or all waiting (optionally per folder), and Try again per job or for all failed. The queue reads each file itself before running the assistant, so unreadable files fail and can be retried; when the model cannot be reached the job goes back and the queue waits 30 s doubling to 10 min (`INGEST_RETRY_SECONDS`), with Try now
- **Watched folders (`lib/watcher.ts`)**: folders on the server, added on Settings (Windows paths are translated for WSL). Every `WATCH_INTERVAL_SECONDS` (default 60) each enabled folder is walked; files whose size or time changed are hashed, and new content is stored and queued as document `folder:<label>:<relative path>`. Files changed in the last 10 seconds wait for the next scan; hidden files, Office lock files, system files (`desktop.ini`, `Thumbs.db`) and program internals (`__pycache__`, `site-packages`, virtual environments, `.app` and similar bundles) are skipped, down to 20 folders deep. Files the wiki cannot read (models, raw data, code) are listed by name and size in `folder_other_files`, never read, so the folder tree and plans see the whole folder. The folder is never written to. When a folder file is filed, `lib/folderContext.ts` gives the assistant its label, path, neighbouring files and a compact outline of the folder tree (from `watched_files`, trimmed to the path and its surroundings for large trees), as a hint about placement rather than a structure to copy
- **Filing plans (`lib/filingPlan.ts`)**: reading every file with the assistant is slow and mostly wasted on look-alike files and raw data, so each folder inside a watched folder has a rule in `folder_rules`, and a file follows its nearest folder's rule: `file` (default), `sample` (look-alike groups: the first 2 of each kind, by file name with numbers replaced, are filed and the rest kept searchable), `index` (kept searchable, status `kept`, no assistant; photos and scans are not read) or `skip` (not read; skipped at scan time, never copied). Rules come from patterns (`patternRules`: five or more sub-folders holding the same kind of files, camera photo runs, numbered series), then from a `plan` job (`ingest_jobs.mode = 'plan'`, run before anything else and while paused) where the assistant reads the folder outline once and answers one line per folder, then from people; a person's rule is never overwritten. A folder gets a plan when it is added and at startup if it has none. Rules are applied when a job comes up, so waiting files follow rules set after they were queued; `refile` sends what a changed rule skipped back to the queue. Text that is mostly numbers is skipped as raw data. Files over 12,000 characters reach the assistant in parts of about 8,000 (part 1 plus a line on each other part); it reads on with `read_file_part` only when worth it. API: `/api/folders/:id/plan`. Settings shows Background filing By folder (`components/FolderPlan.tsx`): each watched folder as a tree with each folder's rule, its reason and who set it, what happened to its files, a rule picker, Plan again, and File these now on folders whose own rule was loosened
- **Document lookup (`lib/docsearch.ts`)**: the latest version of every document is indexed in ~1500 character parts in `documents_fts` when a version is recorded (and at startup for any not yet indexed). The `search_documents` and `read_document` tools let the assistant answer from originals; it must say such answers are not in the wiki yet. A document read during a run becomes a source of anything suggested in that run
- **Live updates**: chat requests run on the server (`lib/runs.ts`), so closing the chat does not stop them; the chat reconnects via `/api/chat/runs/:id`. `lib/pulse.ts` counts changes and open pages poll `/api/pulse` to refresh
- **Structure and summaries (`lib/structure.ts`)**: the wiki's structure is never written by hand. The home page shows it as Contents (`components/Contents.tsx`, `/api/structure`; `/structure` redirects there), generated from the pages, so it is always current. What people and the assistant write is each page's summary: its opening prose paragraph under the title (`summaryOf`, `withSummary`), saying what the page or section covers and what belongs in it. A summary can be changed but never removed, and a new page needs one (`summaryProblem` in `lib/summary.ts`, checked on human saves and on the assistant's edits); pages show it apart at the top, and the editor has a Summary box above the page text. People edit summaries in place in Contents (published at once); the assistant's `set_summary` stages one, and on a path with no page it proposes a new section page. Filing gets `structureOutline` (sections with summaries) to decide where things go
- **Librarian (`lib/librarian.ts`)**: two jobs. **Organise** (scope `*`, the architect) designs the layout of the whole wiki: which sections exist, what belongs in each, and homes for topics the watched folders show are still coming; it may only use reading tools, `set_summary` and `move_page` (`ORGANISE_TOOLS`), and reports splits, merges and rewrites for others. **Tidy** (one section, the cleaner) works inside that layout: duplicates, stubs, pages that do not fit the section's summary, splits, missing summaries, broken links. `surveySection` works out hints without a model: pages that share wording (three-word runs) or vocabulary, pages that read more like another section, folders without a page or summary, very short pages, links to pages that do not exist, and a map of the watched folders (trees with file counts and how many are not filed yet, from `watched_files` and `documents`, and which wiki sections each folder's filed pages ended up in, from `page_sources`). Runs are `ingest_jobs` with `mode = 'tidy'` (no file; doc key `tidy:<scope>`, `tidy_limit`), taken ahead of waiting files and run even while filing is paused, one per scope at a time. The agent gets the Organise or Tidy addendum to its prompt, about three steps per page it may change (up to 100), and older tool results shortened so long runs fit a local model's context. The limit on pages per run is a Settings value (`librarian.limit`, default 25, max 50; `ToolContext.limit`); in chat, calling `survey_section` sets the same limit. `move_page` also moves a folder of pages with no page of its own. Suggestions get a `librarian` source naming who started the run, and it never sees personal documents
- **Librarian on its own (`lib/librarianAuto.ts`)**: on unless turned off on Settings (`librarian.auto`). Every `LIBRARIAN_CHECK_SECONDS` (300) it queues at most one run as user `Librarian`: the whole wiki first, then each section, for a part whose last git change is older than `LIBRARIAN_QUIET_SECONDS` (30 min) and newer than its last tidy, at most every `LIBRARIAN_WHOLE_GAP_SECONDS` (24 h) or `LIBRARIAN_SECTION_GAP_SECONDS` (2 h). It waits while files are being filed (a paused backlog does not count), skips a part that still has librarian suggestions waiting for review, and its runs end without asking the model when the survey finds nothing. `POST /api/librarian {action: "check"}` runs the check at once
- **Personal folders**: a watched folder is `wiki` or `personal` (owner = the folder's user). Personal files get index-only jobs (`ingest_jobs.mode = 'index'`, document key `personal:<label>:<path>`, `documents.personal`/`owner`), never run the assistant, and are searchable only in the owner's chat. Reading a personal document sets `personalRead`, after which every wiki-changing tool refuses for that run. Switching a folder to wiki can file its existing documents. The owner is the signed-in account that added the folder
- **Sign-in and roles (`lib/auth.ts`, `app/api/login`, `app/api/me`, `app/api/users`)**: accounts live in SQLite (`users`: name, role, scrypt passcode hash; `sessions`: random token, 30-day expiry). The login page (`/login`) signs in, or sets up the first account as an admin when none exist. Three roles, each including the last: **viewer** reads, searches, chats; **editor** also edits pages, reviews suggestions, drops files, watches folders; **admin** also manages Settings (`/api/settings*`, librarian settings) and people (`/api/users`). Every API route goes through `requireUser(req, minRole)` in `lib/api.ts`, which reads the `aiwiki_session` HttpOnly cookie; the session user's name is what edits, approvals and suggestions are recorded under, so request-body `user` fields are ignored (the e2e script logs each identity in). The browser learns who it is from `/api/me`; an unsigned shell redirects to `/login`. Signing out is `DELETE /api/login`
- **`lib/settings.ts`**: Settings page values (local model address, model, key) stored in SQLite, overriding `.env.local`
- **Choosing a place (`components/PlaceDialog.tsx`)**: New page and Move never ask for a typed path. People type a title and pick a place in the page tree; the path is worked out from both, and a move with a new title also changes the page's heading. Breadcrumbs show titles. Links follow moves (see Page structure)
- **`components/`**: `Shell` (mounted once from `app/wiki/layout.tsx` so chat survives navigation), `Sidebar`, `PageView` (inline review), `wordMarks` (changed-word highlights), `ChatPanel`, `SourceChip`, `Md` (markdown plus `[[wiki links]]`)

## Rules that must not break

1. **Markdown in git is the source of truth.** SQLite holds search, proposals and provenance; never live page content.
2. **The AI never writes to the wiki.** Its tools only stage proposals. Only a human approval calls `writePage`. Any new AI capability (file ingest, folder watching) must go through `createSource`, then `createChangeSet`, then `stageContent`.
3. **Approval happens inline on the page.** No separate review screen, queue page or diff viewer. The sidebar badge is the only pointer to pending work.
4. **Never expose git concepts in the UI.** No branches, commits, hashes or "diff" wording. Reviewers see highlighted changes and Approve or Reject.
5. **Every proposal links to a source record**: who contributed it, the watched folder label and relative path (never a full local path), filename, content hash, version and time. Approvals copy the source into `page_sources` and into the git commit message.
6. **Stay provider-neutral.** The agent loop and tools must work with both providers. Do not use Anthropic-only features in the shared path.
7. **Human edits publish immediately** and are committed under the editor's name.

## Conventions

- Keep the software general: it must work for any team's knowledge base. Never code against one deployment's folders, file names, file types or topics; tune with patterns any knowledge base has (look-alike files, raw data, program folders), and leave anything specific to the plan, the rules people set and the summaries
- Never use an em dash anywhere: UI copy, docs, code comments, commit messages. Use a semicolon or rework the sentence
- UI copy: plain sentence case, active verbs, buttons name the action ("Approve all", "Save page")
- Keep the visual style: IBM Plex Sans for UI, Source Serif 4 for page content, teal accent, green additions, red struck-through removals
- Layout must work at phone width
- Small, focused commits; one feature per commit

## Testing

`npm run e2e` (`scripts/e2e.mjs`) starts `scripts/mock-llm.mjs` and a dev server on a throwaway data directory, then drives `/api/chat`, `/api/page` and `/api/proposals/:id/hunk|resolve`. The mock answers both the OpenAI-compatible and the Anthropic Messages formats from keyword-picked scenarios, and rejects Anthropic tool loops that drop thinking blocks or split tool results. Run it after any change to proposals, the diff, or the agent; add a scenario to the mock when you add a flow.

## Known gaps (do these first)

1. **Filing plans have only been planned by the mock.** Check what a real model answers for a real watched folder (one line per folder in the `folder | rule | reason` form; `parsePlan` ignores anything else) and whether its skip and sample choices are sensible; widen `parsePlan` if a model words it differently. Patterns already sample the capture runs without a model.
2. The Anthropic adapter has not run against the real API (mock-checked only). Not needed right now — revisit when Anthropic becomes a live provider; the check is a full propose-and-approve cycle with a real key.

Settled 2026-10-24: local model cycle works (qwen); photos and scans verified with a real vision model; a librarian section tidy ran with a real model; Node 22 is what start.sh installs; a deleted watched file suggesting removals is deliberately left out for now.

## Roadmap, in order

1. **Sign-in with roles** — landed 2026-10-24 (accounts, three roles, all routes guarded; personal folders owned by the signed-in account). Remaining: an external sign-in (Entra ID SSO) can replace the login page later without touching the plumbing.
2. **Link picker in the editor**: links are still typed as `[[page/path]]`; add an "Insert link" button that picks a page from the same tree as the place picker and inserts the link, so nobody types a path (links already follow moves)
3. **Conflict handling**: when sources disagree, the proposal cites both and flags the conflict instead of silently picking one
4. **Bulk review** for large drops: a per-source summary and one approval for a whole change set across pages
5. **Companion desktop app** (only needed when the wiki server cannot reach the model; a model on the server itself or on a machine it can reach on the network already works through `LOCAL_LLM_BASE_URL`): watches folders on a user's machine (SharePoint libraries via the OneDrive sync client, with Files On-Demand off for that folder), uploads to the queue with the user's identity, and relays calls to a local model so a remote wiki can use AI on the user's own computer
